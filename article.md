# Что Claude Code хранит на диске и как проверить права, не открывая токен

Если Claude Code перестал пускать в аккаунт, совет «почистить конфиг» звучит правдоподобно. Но за словом «конфиг» здесь прячутся разные вещи. В одном файле лежат настройки, в другом CLI хранит состояние проектов, а у файла входа в Linux есть вполне конкретное требование к правам. Последнее можно проверить одной командой, даже если терминал сейчас видят коллеги на демонстрации экрана.

Я собрал небольшой Bash-скрипт для такой проверки и прогнал его в контейнере с искусственным профилем. Вот что удалось подтвердить по документации и что на самом деле показывает отчёт.

## Четыре похожих имени

| Где | Что там находится | Когда это имеет значение |
| --- | --- | --- |
| ~/.claude/settings.json | Пользовательские настройки CLI | Параметры действуют в разных проектах одного пользователя. При стандартной установке файла может ещё не быть. |
| .claude/settings.json и .claude/settings.local.json в проекте | Общие настройки проекта и индивидуальные параметры для этой рабочей копии | У двух разработчиков одного репозитория поведение CLI может различаться. |
| ~/.claude.json | Сведения об аккаунте, конфигурация MCP-серверов, состояние проектов, в том числе решения о доверии | Удаление файла может затронуть подключённые инструменты и заставить заново подтвердить доверие проектам. |
| ~/.claude/.credentials.json в Linux | Учётные данные для входа | Для диагностики прав достаточно посмотреть метаданные файла. Его содержимое в отчёте не требуется. |

Пути в таблице относятся к стандартному расположению. Если указан CLAUDE_CONFIG_DIR, CLI ищет пользовательские настройки и файл учётных данных в настроенном каталоге. Проектные настройки по-прежнему ищут в самом проекте. [Настройки и области их действия](https://code.claude.com/docs/en/settings) · [Документация по авторизации](https://code.claude.com/docs/en/authentication).

## Что можно доказать по файлу на диске

В обсуждениях версии 2.1.284 встречается утверждение, что по локальным полям userID и machineID можно определить, какие идентификаторы уходят с каждым запросом модели. В реестре действительно есть официальный пакет этой версии. Карточка пакета подтверждает выпуск, но ничего не сообщает о составе конкретного запроса. Сетевой обмен этой сборки я не измерял. Формат значения, его назначение внутри программы и факт его передачи — три отдельных утверждения, для каждого нужны свои наблюдения. [Карточка версии в npm](https://registry.npmjs.org/@anthropic-ai/claude-code/2.1.284).

Отсюда практическая развилка. Если CLI сообщает об ошибке чтения JSON, документация описывает восстановление глобальной конфигурации из резервной копии. Если при входе сервис прямо сообщает о приостановке аккаунта, Anthropic принимает апелляцию через страницу этого аккаунта. Даже автор разбора Windows-утилиты на Пикабу отдельно оговаривает, что локальная операция не снимает серверную блокировку. [Восстановление настроек](https://code.claude.com/docs/en/settings) · [Порядок апелляции](https://support.claude.com/en/articles/8241253-safeguards-warnings-and-appeals).

## Что нашёл скрипт в тестовом профиле

Для проверки я создал в контейнере пустые файлы пользовательских настроек и учётных данных. Выставил обоим режим 644, проектные настройки создавать не стал. Содержимого у файлов не было вовсе, так что результат зависит только от их расположения и прав:

```text
user-settings: present, mode 644
credentials: present, mode 644 (expected 600)
project-settings: not found or unreachable
project-local-settings: not found or unreachable
```

Цифра 6 в первой позиции означает чтение и запись для владельца, две четвёрки дают чтение группе и остальным пользователям. Может ли сосед по серверу действительно прочитать файл, зависит ещё и от доступа к родительским каталогам. Но расхождение с документированным режимом 600 уже видно. Когда я выставил тестовому файлу 600, предупреждение исчезло, код выхода сменился с 1 на 0.

Скрипт запускают из каталога проверяемого проекта. Он печатает только четыре фиксированные метки, статус и права найденных файлов. Поэтому в этот вывод не попадут домашний путь, адрес почты или строка токена. Для самого запуска не нужны авторизация в Claude или права администратора. [Скрипт и инструкция](https://github.com/stufently/claude-code-config-audit).

## Почему один и тот же отчёт нельзя переносить с Linux на macOS

В macOS обычное место хранения данных входа — системная связка ключей. Anthropic отдельно описывает случай, когда она отклоняет запись, например при работе по SSH с заблокированной связкой. Для некоторых способов входа CLI тогда использует файл с режимом 600. В Windows документация указывает на права доступа, унаследованные от каталога профиля. Поэтому проверку числового режима я ограничил Linux. [Хранение данных входа на разных платформах](https://code.claude.com/docs/en/authentication).

Для обращения в поддержку из этого получается короткий и воспроизводимый отчёт: платформа, версия CLI, текст ошибки и строка о правах нужного файла. Если вопрос был в том, почему файл доступен группе, этих данных хватает, чтобы начать разбираться. Выводить содержимое файла ради ответа не потребовалось.
